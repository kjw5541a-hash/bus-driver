# 버스 물리 + 입력 설계

작성일: 2026-09-23
서브프로젝트: 2 / 7 (구운 도시 위를 사람이 직접 모는 버스)

## 배경

1번 서브프로젝트가 OpenStreetMap 데이터를 `assets/routes/route_<id>.glb` 와
`route_<id>.json` 으로 굽는 오프라인 파이프라인을 완성했다. 서울 3개 노선
(서대문03, 100, 654)이 구워져 저장소에 들어 있고, 헤드리스 검증에서 지면
커버리지 99.9% 이상과 정류장 이름 100% 를 통과했다.

1번이 만든 버스는 산출물을 검증하기 위한 자율주행 하네스일 뿐이다. 이 문서는
그것을 사람이 모는 버스로 바꾸고, 노선을 골라 실제로 달릴 수 있는 최소 게임을
만드는 일을 다룬다.

전체 분해에서 이 문서의 자리:

1. OSM 베이크 파이프라인 — 완료
2. **버스 물리 + 입력** ← 이 문서
3. 정류장·승객 시스템
4. 신호·위반 시스템
5. 시간표·점수·종착 판정
6. 교통 AI / 단속
7. 노선 선택 메뉴, 3개 노선 굽기, 배포

## 목표와 비목표

**목표**

- 무게감 있는 세미 리얼 버스 물리. 회전 반경이 실제 시내버스 수준이라 급한
  코너에서 후진이 필요해진다.
- PC 키보드와 안드로이드 터치를 같은 내부 축으로 받는 입력 계층.
- 노선 3개를 고를 수 있는 최소 메뉴와, 고른 노선을 달리는 주행 씬.
- 지면에 깔리는 내비 라인. 실제 서울 지도 위에서 길을 잃지 않게 한다.
- PC 에서 seoul-100 을 60 fps 로 돌린다.

**비목표**

- 정류장 정차·승객 승하차(3번), 신호 동작(4번), 시간 제한·점수·완주 판정(5번),
  교통 AI(6번). 종점에 도착해도 이 서브프로젝트에서는 아무 일도 일어나지 않는다.
- 안드로이드 실기 검증. 빌드는 되게 하되 실제 기기에서 재지 않는다.
- 엔진음·효과음.
- 충돌 손상. 건물에 박아도 튕기기만 한다.
- 청크 거리 컬링. 측정이 요구할 때만 넣는다(아래 "성능" 참조).

## 1번에서 이어받는 사실

전부 실측으로 얻은 값이다. 추측으로 바꾸지 않는다.

- **좌표계.** 로컬 평면 미터. x 동쪽, z 남쪽, y 는 0 고정. 원점은 노선 bbox 중심.
- **`engine_force` 부호가 반대다.** Godot 4.7 `VehicleBody3D` 는 음수
  `engine_force` 가 차량 전방(로컬 −Z)으로 민다. 그 상태에서 `steering` 부호도
  뒤집힌다. 1번에서 이걸 모르고 커브마다 도로를 이탈했다.
- **서스펜션.** 12 t 차량은 기본값(바퀴당 6 kN, 4륜 합계 24 kN)으로 주저앉는다.
  무게가 117 kN 이다. `suspension_stiffness = 150`,
  `suspension_max_force = 80000`, `damping_compression = 3.7`,
  `damping_relaxation = 6.1`, `wheel_friction_slip = 3.5` 로 버틴다.
- **차체 충돌 상자를 띄워야 한다.** 밑면이 지면에 닿으면 바퀴가 일을 못 한다.
  상자 크기 2.5 × 3.0 × 11.0, 중심을 y = 2.0 에 둔다.
- **휠베이스 6.6 m.** 앞바퀴 z = −3.6, 뒷바퀴 z = +3.0, 좌우 ±1.1, 반경 0.5 m.
- **도로 밖은 허공이다.** 산출물의 충돌면은 도로 리본과 건물뿐이다. 1번 하네스는
  도로를 벗어나지 않게 짜여 있어 이 문제가 드러나지 않았다.
- **데이터 계약.** `route_<id>.json` 의 `route` 는 `[[x, z], ...]`,
  `stops` 는 `progress_m` 오름차순, `chunks` 는
  `[{"name", "min", "max"}, ...]`.

## 아키텍처

씬 둘, 스크립트 여섯.

```
scenes/menu.tscn   + scripts/menu.gd      노선 버튼 3개, 고른 id 를 drive 씬에 넘긴다
scenes/drive.tscn  + scripts/drive.gd     주행 씬 조립: 도시, 버스, 카메라, 내비 라인
scripts/route_data.gd     route_<id>.json 을 읽어 경로·정류장·메타를 담는다
scripts/city.gd           .glb 인스턴스화, 충돌 메쉬 생성, 바닥 평면
scripts/bus.gd            VehicleBody3D 확장. 축 세 개를 물리로 번역한다
scripts/bus_input.gd      플랫폼 입력 → 축 세 개
scripts/chase_camera.gd   SpringArm3D 기반 추격 카메라
scripts/nav_line.gd       route 폴리라인을 지면 위 반투명 리본으로
```

경계가 서는 지점 셋:

**`bus_input.gd` 가 입력을 독점한다.** `bus.gd` 는 `steer`(−1..1),
`throttle`(0..1), `brake`(0..1), `reverse`(bool), `respawn`(단발) 만 본다. PC 냐
터치냐를 `bus.gd` 는 모른다. 입력 매핑이 순수 계산으로 남아 헤드리스 테스트가
가능해지고, 5번에서 HUD 가 계기판을 그릴 때도 같은 통로를 쓴다.

**`city.gd` 가 충돌 메쉬 생성을 독점한다.** 지금 `tests/bake/verify.gd` 안에 박혀
있는 로직을 꺼내는 것이다. 청크 노드 목록을 쥔 유일한 곳이므로, 거리 컬링이
필요해지면 들어갈 자리도 여기다.

**`route_data.gd` 가 JSON 키를 독점한다.** 1번의 데이터 계약을 읽는 유일한
지점이라, 계약이 바뀌어도 한 파일만 고친다.

## 버스 물리

1번의 값을 그대로 쓰되 넷을 바꾼다.

**질량 중심을 낮춘다.** 자율주행은 전복하지 않았지만 사람이 몰면 급회전에서
뒤집힌다. `center_of_mass_mode = CENTER_OF_MASS_MODE_CUSTOM` 으로 y = 0.5 에 둔다.
충돌 상자 중심(y = 2.0)보다 한참 아래다.

**최대 조향각을 줄인다.** 목표는 각도가 아니라 **회전 반경 9–11 m** 다. 실제
시내버스가 그 정도다. 자전거 모델 `R = L / tan(δ)` 에 휠베이스 6.6 m 를 넣으면
δ ≈ 0.6–0.65 rad 이다. 1번 하네스의 0.9 rad 은 반경 5.2 m 로 실제 버스보다 훨씬
민첩했다. **이 숫자가 이 서브프로젝트의 핵심이다** — 급한 코너에서 한 번에 못 돌아
후진이 필요해지는 긴장이 여기서 나온다.

시작값 `MAX_STEERING = 0.62`. 회전 반경 테스트(아래)가 9–11 m 를 확인한다.

**속도 감응 조향.** 정지 상태에서 최대각을 다 쓰고, 속도가 오를수록 좁힌다.

```
steer_limit = MAX_STEERING * lerp(1.0, 0.3, clamp(speed / 16.7, 0, 1))
```

16.7 m/s 는 60 km/h 다. 안 하면 고속에서 조금만 밀어도 스핀한다.

조향은 즉시 바뀌지 않고 초당 `STEER_RATE = 1.5 rad` 로 제한한다. 1번에서 급커브
직후 S 자 구간에 한 프레임 만에 반대쪽으로 꺾이는 문제를 막으려고 넣은 값이다.

**후진.** `reverse` 가 켜져 있으면 `engine_force` 부호를 뒤집는다. `steering` 은
건드리지 않는다 — 실제 차처럼 앞바퀴가 향한 쪽으로 차가 밀려간다. PC 는 정지
상태(속도 0.5 m/s 미만)에서 `S` 를 계속 누르면 후진으로 전환되고, 터치는 전용 토글
버튼을 쓴다. 후진 중에는 `S` 가 뒤로 미는 구동이 되고, `W` 를 누르면 전진으로
돌아온다. 속도 0 을 복귀 조건으로 쓰지 않는다 — 후진을 멈춘 순간 제자리에서
전진으로 튀어버린다.

**최고 속도** `MAX_SPEED = 19.4 m/s`(70 km/h). 넘으면 `engine_force = 0`. 시내버스가
그 이상 나갈 일이 없고, 안 막으면 직선에서 무한 가속한다. 후진은 `MAX_SPEED` 의
30% 로 따로 제한한다.

**구동력** `ENGINE_FORCE = 30000` N. 1번 하네스에서 12 t 을 9 m/s 까지 실용적인
시간에 올린 값이다. 제동은 `BRAKE_FORCE = 40.0`.

## 주행면과 리스폰

**바닥 평면.** `WorldBoundaryShape3D` 를 가진 `StaticBody3D` 하나를 y = 0 에 깐다.
도로를 벗어나도 맨땅 위를 달릴 뿐 떨어지지 않는다. 건물은 그대로 벽으로 남는다.
무한 평면이라 비용이 없고, 도로 리본(두께 0)과 같은 높이라 턱이 생기지 않는다.

**리스폰.** 끼거나 뒤집히면 가장 가까운 경로점으로 노선 방향을 보게 되돌린다.
세미 리얼로 가면 반드시 끼는 순간이 오고, 그때 재시작밖에 없으면 게임이 아니다.

- 위치: 버스에서 가장 가까운 `route` 점, y = 1.5 위
- 방향: 그 점에서 다음 점을 향해
- 속도·각속도 0 으로 초기화
- PC `R`, 터치는 전용 버튼

되돌리기만 하고 벌점은 없다. 패널티는 5번이 정한다.

## 입력

`bus_input.gd` 가 내는 것은 축 세 개와 플래그 둘뿐이다.

**PC**

| 키 | 동작 |
|---|---|
| `W` | 가속 |
| `S` | 제동. 정지 상태에서 계속 누르면 후진 |
| `A` / `D` | 조향 |
| `R` | 리스폰 |

주차 브레이크는 넣지 않는다 — 할 일이 없다.

**안드로이드 터치**

화면 **왼쪽 절반 아무 데나** 손가락을 대면 그 지점이 조향 중립이 된다. 좌우 변위가
조향각이고, 화면 폭의 15% 를 끌면 최대 조향이다. 손가락을 떼면 중립으로 돌아간다.
고정 위치 스틱이 아니라 터치 지점을 중립으로 잡는 이유는, 화면을 안 보고 엄지를
내리면 고정 스틱은 빗나가기 때문이다.

오른쪽에 버튼 넷: 가속(큰 원), 제동(큰 원), 후진 토글(작게), 리스폰(작게).

PC 에서 터치 경로를 확인하려면 `input_devices/pointing/emulate_touch_from_mouse`
를 켠다. 실기 검증은 하지 않는다.

**축 계산.** `steer` 는 터치 변위를 화면 폭 15% 로 나눠 −1..1 로 자른 값, 키보드는
−1 / 0 / +1. 둘 중 활성인 쪽을 쓰고, 동시에 들어오면 터치를 우선한다.

## 카메라

`SpringArm3D` 를 버스에 달고 그 끝에 `Camera3D` 를 둔다. 뒤 12 m, 위 6 m, 약간
내려본다. 스프링암이 건물 관통을 알아서 처리하므로 레이캐스트를 직접 짜지 않는다.

버스 요(yaw)를 즉시 따라가지 않고 지연 추종해서 커브에서 살짝 늦게 따라온다.
1인칭·측면 전환은 넣지 않는다.

## 내비 라인

`route` 폴리라인을 폭 1.5 m 리본 메쉬로 만들어 y = 0.05 에 깐다. 도로면과
z-fighting 을 피하는 높이다. 반투명 파랑, `shading_mode = unshaded`.

seoul-100 기준 경로점 636개라 삼각형 1.3k 수준이고, 통짜 메쉬 하나면 된다.
정류장 마커는 3번 서브프로젝트 것이라 넣지 않는다.

## 메뉴

버튼 세 개짜리 최소 화면이다. 각 버튼은 `assets/routes/` 의 노선 JSON 에서 읽은
`name` 과 `from` → `to` 를 표시한다. 누르면 주행 씬을 그 노선으로 연다.

노선 목록은 하드코딩하지 않고 `assets/routes/*.json` 을 훑어서 만든다. 4번째 노선을
구우면 메뉴가 알아서 늘어난다.

`project.godot` 의 `run/main_scene` 을 지금의 `tests/bake/verify.tscn` 에서
`scenes/menu.tscn` 으로 바꾼다.

## 성능

측정이 결정한다. 먼저 컬링 코드 **없이** 붙이고 잰다.

seoul-100 은 삼각형 133k, 청크 643개다. Godot 는 `MeshInstance3D` 단위로 절두체
컬링을 공짜로 하므로, `.glb` 를 그냥 인스턴스화하는 것만으로 컬링이 상당 부분
이미 된다.

기준: PC 창 모드에서 seoul-100 주행 중 **평균 60 fps, 최저 55**.

- 통과하면 청크 거리 컬링을 구현하지 않는다.
- 미달이면 `city.gd` 에 200 m 청크 거리 기반 `visible` 토글을 넣고 다시 잰다.
  `chunks` 의 AABB 가 이미 JSON 에 들어 있어 거리 계산은 공짜다.

## 검증

세 층이다. 1번의 `verify.gd` 패턴(헤드리스 실행 후 `OK` / `FAIL` 출력하고 종료)을
그대로 재활용한다. GUT 같은 테스트 프레임워크는 붙이지 않는다.

**1. 입력 매핑 유닛 테스트** (`tests/game/test_input.tscn`)

`bus_input.gd` 의 축 계산은 순수 계산이라 헤드리스로 단언할 수 있다.

- 키보드 좌/우가 `steer` −1 / +1 을 낸다
- 터치 변위 0 / 화면폭 7.5% / 15% / 30% 가 각각 `steer` 0 / 0.5 / 1.0 / 1.0
- 터치를 떼면 `steer` 가 0 으로 돌아간다
- 정지 상태에서 제동을 계속 누르면 `reverse` 가 켜진다
- 주행 중 제동은 `reverse` 를 켜지 않는다

**2. 주행 스모크 테스트** (`tests/game/drive_smoke.tscn`)

`drive` 씬을 헤드리스로 띄우고 1번의 자율주행 조향 로직으로 축을 먹여 seoul-100 을
달린다. 판정:

- 씬 조립 성공(도시·버스·내비 라인이 모두 존재)
- 100 m 이상 전진
- y 가 −5 아래로 내려가지 않는다

1번과 같은 이유로 완주는 요구하지 않는다. 최대 조향각이 0.62 rad 로 줄어 하핀은
더 못 돈다.

**3. 회전 반경 테스트** (`tests/game/test_turn_radius.tscn`)

빈 평면 위에 버스를 놓고 `steer = 1.0`, 낮은 일정 속도로 한 바퀴 돌린다. 궤적의
지름을 재서 반경이 **9–11 m** 밖이면 실패한다. 이 서브프로젝트의 핵심 숫자라
자동으로 지킨다.

**4. 성능 측정** (`tests/game/measure_fps.tscn`)

헤드리스로는 의미가 없으므로 창 모드로 돌린다. seoul-100 을 자율주행으로 달리며
`Engine.get_frames_per_second()` 의 평균과 최저를 출력한다. 판정은 사람이 본다.

**사람이 판정하는 것.** 조작감은 자동으로 잴 방법이 없다. 구현이 끝나면 직접 몰아
보고 회전 반경·가속·카메라 지연을 조정하는 항목을 남긴다. 이 조정은 검증 실패가
아니라 튜닝이다.

## 알려진 한계

전부 의도적인 단순화다.

- **안드로이드 실기 미검증.** 마우스 에뮬레이션으로만 확인한다. 실기에서 터치 좌표
  스케일이나 성능이 다를 수 있다.
- **소리 없음.** 엔진음이 조작감에 크게 기여하지만 에셋이 없다.
- **충돌 손상 없음.** 건물에 박아도 튕기기만 한다. 위반·손상은 4번과 6번이다.
- **차선 없음.** 1번 산출물이 폭만 있는 통짜 리본이라 중앙선이 없다. 역주행 개념이
  성립하지 않는다.
- **청크 거리 컬링 미구현.** 측정이 요구하면 그때 넣는다.
- **리스폰에 벌점 없음.** 5번이 정한다.

## 완료 기준

1. 메뉴에서 노선 3개를 고르면 해당 주행 씬이 뜬다
2. 키보드로 몰아 도로를 따라 달릴 수 있다
3. 최대 조향 회전 반경이 9–11 m 다 (자동 테스트)
4. seoul-100 에서 평균 60 fps, 최저 55 이상 (PC 창 모드 측정)
5. 도로를 벗어나도 떨어지지 않고, 리스폰이 동작한다
6. 터치 입력이 마우스 에뮬레이션에서 동작한다
7. 헤드리스 테스트가 전부 통과한다
